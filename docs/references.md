## Building/shipping Mac and iOS apps without opening Xcode

- **Source**: [scottwillsey.com](https://scottwillsey.com/building-and-shipping-mac-and-ios-apps-without-ever-opening-xcode/), discussed on [Hacker News](https://news.ycombinator.com/item?id=48896665)
- **Found**: 2026-07-13
- **Covers**: `xcodebuild`/`xcodegen`/`xcrun notarytool`/`xcrun stapler`/`codesign`/`spctl`/`devicectl` as a full CLI-only Mac/iOS build-sign-notarize-ship pipeline, driven end to end by Claude Code through a plain non-interactive shell.
- **Adopted**: `profiles/ios/skills/release-macos-spm-packaging/SKILL.md` was missing the `xcrun notarytool store-credentials` one-time setup step and post-release verification (`codesign -dv --verbose=4`, `spctl -a -vvv -t exec`, `xcrun stapler validate`) — added both, plus the "needs full Xcode.app, not just Command Line Tools" caveat (also raised independently in the HN thread).
- **Still open, not acted on** (no current fleet evidence, so not built speculatively — matches the harness's own `macos-ci-recipes` precedent of waiting for real usage before shipping a recipe):
  - A Developer-ID-notarized **direct distribution** pipeline (outside the App Store) for a macOS app that **does** have an Xcode project. `release-macos-spm-packaging` only covers the no-`.xcodeproj` SwiftPM path; `release.yml` only covers App Store/TestFlight submission via the App Store Connect API. Nothing currently covers "Xcode-project macOS app, shipped as a notarized `.zip`/`.dmg` outside the App Store." Revisit if/when a fleet project actually needs this.
  - The article's XcodeGen pattern (gitignore `.xcodeproj`, regenerate from `project.yml` via `xcodegen generate` on every build) is **not** this repo's current model — the harness assumes a committed `.xcodeproj` (`internal/detect`, the `{{XCODEPROJ}}` token, the `.claude/settings.json` hook blocking `.pbxproj` edits). `project.yml` is already referenced in `CLAUDE.ios.md`'s Secrets section, but as a committed input file, not a gitignored-and-regenerated one. Switching models would be a real architectural change, not a docs tweak — don't do it opportunistically.
- **HN thread gotchas worth remembering** (not yet acted on anywhere):
  - Running an AI agent with broad Mac/filesystem access is a real, repeatedly-raised risk (cited example: a home directory including SSH keys getting uploaded by an agent). Mitigations discussed: a separate restricted user, a VM/container (Tart, VirtualBuddy, Apple containers), Secure Enclave-backed SSH keys (Secretive.dev). Directly relevant to how this repo already reasons about subprocess-invoking rescue skills (see `core/skills/antigravity-rescue/SKILL.md`'s Security section) — worth keeping in mind if a similar sandboxing question comes up again.
  - XcodeGen has known reliability gaps on complex projects (widgets, watchOS, notification extensions) — another reason not to switch this repo's model opportunistically.
  - Sideloaded/ad-hoc-signed apps expire weekly/biweekly and need re-signing — not relevant to this fleet's TestFlight/App-Store-based distribution today, but worth knowing if that ever changes.

## Agentic device-automation / Apple-dev toolkits (Axiom, argent, agent-device)

- **Sources**:
  - [Axiom](https://charleswiltgen.github.io/Axiom/) ([tools page](https://charleswiltgen.github.io/Axiom/tools/)) — Charles Wiltgen
  - [software-mansion/argent](https://github.com/software-mansion/argent)
  - [callstack/agent-device](https://github.com/callstack/agent-device)
- **Found**: 2026-07-13
- **Covers**:
  - **Axiom** — a large (158 discipline + 80 reference + 26 diagnostic skills, 41 agents, 15 commands), MIT-licensed, Claude-Code/Codex-oriented collection specifically for modern Apple OS dev (Swift 6, SwiftUI, Liquid Glass, Apple Intelligence). Ships four bundled CLI tools: `xclog` (console capture as JSON), `xcprof` (Instruments trace capture/analysis, wraps `xctrace`), `xcsym` (crash symbolication — `.ips`/MetricKit/`.crash`/`.xccrashpoint`, automatic dSYM discovery), `xcui` (simulator UI/accessibility automation, delegates to AXe for HID input). Still in preview (v27.0.0-beta.22).
  - **argent** (Software Mansion) and **agent-device** (Callstack) — both cross-platform (iOS + Android, some TV/desktop/web) agentic device-control toolkits aimed at AI coding agents; both are primarily React Native-tooling vendors and both tools are RN/Hermes-aware (React DevTools profiling, RN element trees) alongside native support. Different packaging: argent is an MCP server (`npx @swmansion/argent init`); agent-device is a standalone npm CLI with an optional MCP server. Both explicitly position themselves against Appium/Detox/Maestro as "AI-agent-native" rather than traditional automation frameworks.
- **Assessment, not yet acted on**:
  - **argent / agent-device**: likely **not** a good fit for this fleet as-is — this fleet is 100% native SwiftUI/Swift, no React Native anywhere, and both tools' core differentiator (RN/Hermes awareness, Android/TV/Electron breadth) is dead weight here. `flowdeck` (already the mandated tool for all Apple-platform work per `CLAUDE.ios.md`) and `rocketsim` (already a skill) cover the same native-simulator-automation ground more directly. Not recommending adoption unless the fleet ever picks up a cross-platform (RN/Flutter) project.
  - **Axiom**: a genuinely different case — worth a real look before deciding, not dismissed. Two angles, not yet investigated in depth:
    1. **Overlap with the existing `profiles/ios/skills/` set.** Several current skills (`core-data-expert`, `swift-concurrency`, `swift-testing-expert`, `swiftui-expert-skill`, the `xcode-build-*` family) were themselves traced this session to AvdLee's individual per-topic repos (see the skills catalog's Source column) — Axiom may cover the same ground at a different (larger, maintained-as-one-project) grain, which could mean either useful expansion or duplicate content to reconcile.
    2. **`xcsym` (crash symbolication)** looks like a genuinely new capability with no current equivalent anywhere in this repo — `native-app-profiling` covers Instruments/performance, but nothing here handles `.ips`/MetricKit crash report symbolication and triage today.
  - Given the size (~320 items) and that it's still in beta, this deserves a deliberate look (probably a dedicated research/comparison pass) rather than a speculative pull-in — flagging here so it doesn't get lost, not building anything yet.
- **Axiom — resolved, 2026-07-13**: did the deliberate look. Actual structure (verified against the repo tree, not just the docs blurb): 26 top-level "discipline" skills under `.claude-plugin/plugins/axiom/skills/` (`axiom-swiftui`, `axiom-concurrency`, `axiom-data`, `axiom-security`, `axiom-macos`, `axiom-watchos`, `axiom-games`, etc.), each using progressive disclosure into ~130 nested `skills/`/`-ref.md`/`-diag.md` sub-files, plus 40 agents and 15 commands. Duplicated again under `axiom-codex/skills/` for Codex. MIT, 1,059 stars, updated same day as this research — actively maintained.
  - **Not adopting the plugin wholesale.** Its skill content is a broad superset of `profiles/ios/skills/` + the two third-party packages (`dpearson2699/swift-ios-skills`, `HunterHillegas/mac-assed-mac-app-skill`) combined, but two of its four bundled tools directly conflict with tooling already mandated here: `xcui` (simulator UI automation via AXe) and `xcprof` (wraps `xctrace`) do the same job as `flowdeck`+`rocketsim`, which `native-app-profiling`'s own SKILL.md already says to use instead of raw Instruments/`xcrun` tooling. Installing the Axiom plugin would hand agents two competing toolchains for the same job. `xclog` (console capture) likewise overlaps with `flowdeck logs`/`flowdeck run --log`. Pulling in the other ~90 discipline-skill files now would also mean reconciling near-duplicate guidance against the existing curated set for no clear win.
  - **Adopted: `xcsym` only.** Crash symbolication (`.ips`/MetricKit/`.crash`/`.xccrashpoint`, automatic dSYM discovery, `atos`-backed, pattern-tag categorization) confirmed as the one genuinely new capability — nothing else in this fleet does post-mortem crash triage. It's a real, well-tested, zero-dependency Go module (`tools/xcsym/`), same language as `lacquer` itself. No bundled binary distribution exists (no GitHub releases, no Homebrew formula) — vendored as a *skill*, not vendored source: `profiles/ios/skills/xcsym/SKILL.md` + `references/xcsym-reference.md`, following the same external-tool pattern as `flowdeck`/`rocketsim`/`helm-asc` (skill documents usage and how to resolve/build the binary; the tool itself stays external, built from a pinned Axiom checkout).
  - **watchOS and macOS — real gaps, not yet pulled in.** Checked whether `axiom-watchos`/`axiom-macos` would actually be useful against live fleet projects, not just in the abstract:
    - `axiom-watchos` (background/networking, complications, Watch Connectivity, controls/Live Activities, a11y, design conventions) would be **100% net-new** — no watchOS skill exists anywhere in this fleet today (not in `profiles/ios/skills/`, not in either third-party package), and `pixelfox/dailybread` (DailyBread) has a real WatchKit app target confirmed in its `.pbxproj`.
    - `axiom-macos` (AppKit interop/modernization, sandbox & file access, ScreenCaptureKit, menus/commands, windows, Settings scene, SwiftUI-on-macOS differences, direct/notarized distribution) is **mostly net-new** too — existing macOS coverage in this fleet is narrow by design: `macos-ci-recipes` is CI-only, `release-macos-spm-packaging` is packaging/notarization-only, and `HunterHillegas/mac-assed-mac-app-skill` is visual/HIG conventions only ("mac-assedness"), not platform mechanics. `windsock` (macOS-only app), `kit` (SPM macOS app), `mindmint/ios/macOS`, and `repos/Darndest` all have real AppKit/macOS surface that none of the current three sources address.
    - Not built yet — flagging as the natural next pull-in (same "vendor just the skill, not the plugin" treatment as `xcsym`) rather than doing it speculatively in the same pass. Axiom's `axiom-macos`/`axiom-watchos` skills don't wrap a competing CLI tool the way `xcui`/`xcprof` do, so there's no `flowdeck`-mandate conflict to reconcile here — the only work is writing the adapted skill(s).
  - **watchOS and macOS — done, same session.** Vendored both as `profiles/ios/skills/macos-development/` and `profiles/ios/skills/watchos-development/`, each a short `SKILL.md` (agent behavior contract + triage template + routing map, mirroring `core-data-expert`'s shape) plus a `references/` subdirectory per subtopic, rewritten in this repo's voice rather than copied verbatim from Axiom's source. `macos-development`'s `direct-distribution.md` reference explicitly defers to `release-macos-spm-packaging` for the SwiftPM path and frames the Xcode-project direct-distribution pipeline as the still-open gap noted above, rather than silently duplicating or contradicting it. `watchos-development` explicitly defers general SwiftUI to `swiftui-expert-skill`/`swiftui-liquid-glass` and HealthKit/workout specifics to the `healthkit` skill. Catalog rows added to `site/src/content/docs/reference/skills.md`.
  - **License check, same session.** Verified Axiom's actual `LICENSE` file (not just GitHub's SPDX guess): MIT, `Copyright (c) 2025 Charles Wiltgen`. `internal/assets/assets.go`'s `walkInto` distributes every file in a skill directory (not just `SKILL.md`), so a `LICENSE` file placed alongside each vendored skill travels with it into every project `lacquer sync` touches — added one to `xcsym/`, `macos-development/`, and `watchos-development/` (Axiom's exact notice, plus a short pointer to which files it covers and that the content is adapted, not verbatim, for the two discipline-skill ports). This is the first vendored skill in this profile to ship its upstream license text alongside the content — see the note below on the two existing skills where the same check turned up a real problem.
  - **Also found while checking: two already-vendored third-party sources are not MIT, contrary to how they read in the skills catalog.**
    - **`AvdLee/RocketSim-Agent-Skill`** (former source for `profiles/ios/skills/rocketsim/`) has no open license at all — its `LICENSE` file reads "Copyright (c) 2026 SwiftLee. All rights reserved. This repository and all associated source code, documentation, assets, and other materials are proprietary to SwiftLee." GitHub's own detector flags it `NOASSERTION` (not MIT, unlike the sibling AvdLee repos this fleet also vendors from — `Core-Data-Agent-Skill`, `Swift-Concurrency-Agent-Skill`, `Swift-Testing-Agent-Skill`, `SwiftUI-Agent-Skill`, `Xcode-Build-Optimization-Agent-Skill` are all genuinely MIT, confirmed). An all-rights-reserved notice grants no permission to copy, adapt, or redistribute.
      - **Resolved, same day**: rewrote `rocketsim/SKILL.md` as this repo's own thin discovery/delegation wrapper — it locates the installed RocketSim.app and hands off to the Agent-Skill file the app itself bundles (`Contents/Resources/Agent-Skill/SKILL.md`) at runtime, rather than keeping RocketSim's own usage content vendored in this repo at all. No text from the proprietary source remains. This isn't just the license-safe option — it's the better design regardless: the discovery/delegation approach can't drift out of sync with whatever RocketSim build is actually installed, unlike a pinned vendored copy. The "adapted from AvdLee/RocketSim-Agent-Skill" attribution was removed from the skill file and the site catalog since nothing is vendored from it anymore.
    - **`dpearson2699/swift-ios-skills`** (the import-suggested third-party package, installed live via `skills add`, not vendored/copied into this repo) is PolyForm Perimeter License 1.0.0, not MIT — a source-available license that restricts using the software to build a competing product/service, not a permissive open-source license. Lower severity than the RocketSim case since this fleet only *installs and uses* the package as distributed (via the `skills` CLI, referencing the upstream source directly) rather than copying its text into this repo — likely fine under Perimeter's terms for internal use, but the skills catalog's "Third-party skills" section doesn't currently note the license type, which it should for accuracy.

## Dedicated always-on Mac for autonomous Claude Code (claude-controls-mac) and the `dx` plugin

- **Sources**:
  - [ykdojo.github.io/claude-controls-mac](https://ykdojo.github.io/claude-controls-mac/)
  - [ykdojo/claude-code-tips](https://github.com/ykdojo/claude-code-tips) (the `dx` plugin)
- **Found**: 2026-07-18
- **Covers**:
  - **claude-controls-mac** — a guide for setting up a dedicated spare Mac that Claude Code fully controls: SSH access, a tmux server run inside the GUI session to bypass macOS's screen-capture/input permission model, a LaunchAgent for persistence, and `claude --dangerously-skip-permissions`. Safety posture is containment — spare Mac (not the main one), fresh local account, no personal data, no Apple ID signed in.
  - **`dx` plugin** (`ykdojo/claude-code-tips`) — a bundled Claude Code plugin (`claude plugin marketplace add` + `claude plugin install dx@ykdojo`), 8 commands in one install, no partial adoption: `/dx:gha` (CI failure analysis with flakiness/breaking-commit checks), `/dx:handoff` (session handoff docs), `/dx:half-clone` (drops the first half of a long conversation to reclaim context), `/dx:reddit-fetch`, `/dx:review-claudemd` (reviews recent conversations, suggests CLAUDE.md edits), `/dx:hn-summarize`, `/dx:version-check`, `/dx:private-github-search`.
- **Assessment**:
  - **claude-controls-mac**: the core risk it's built around — an agent with broad Mac/filesystem access is dangerous — is the same one already logged above from the Xcode-without-Xcode HN thread, and its mitigation (spare machine, fresh account, no Apple ID) matches what was already discussed there. One real, verified-in-this-repo data point worth carrying into that setup: `core/skills/antigravity-rescue` documents that `--dangerously-skip-permissions`-style flags provide **zero actual enforcement** on at least one CLI (`agy` deleted files inside and outside its allowed directory with or without the flag, verified live on 1.0.6) — don't assume `claude --dangerously-skip-permissions` is a real safety boundary without verifying the same on `claude` itself; the account/OS-level isolation is the boundary that actually holds. Not building anything from this entry — it's a corroborating data point, not a gap.
  - **`dx` plugin — not installing.** One command directly overlaps `github-ci-fix` (`/dx:gha`'s flakiness/breaking-commit framing vs. `github-ci-fix`'s log-pull-and-plan flow — same conflict shape as Axiom's `xcui`/`xcprof` vs. `flowdeck`/`rocketsim`), one needs to rewrite the live session transcript file (`/dx:half-clone`, not something a `SKILL.md` can do), and three are generic productivity unrelated to fleet engineering (`/dx:reddit-fetch`, `/dx:hn-summarize`, `/dx:version-check`). Since the plugin installs all 8 commands as one unit with no cherry-picking, and only 3 of 8 are both novel and a good fit, wrote native equivalents instead: `core/skills/handoff`, `core/skills/claudemd-review` (lighter, single-session complement to `skill-tuning-loop` rather than a replacement), and `core/skills/private-repo-search` (`gh search code`, verified against the installed `gh` CLI's actual flags rather than guessed). `/dx:gha`'s flakiness/breaking-commit capability was folded into `github-ci-fix` directly instead of a fourth new skill, to avoid the same competing-toolchain problem the Axiom research already flagged.
